## 1. Кредитные фичи

### 1.1 Что реализовано
- Capture лида через мини-форму (Phase E): ФИО, телефон, пол, язык, юрлицо, тип
  бизнеса, Telegram, гео, согласие.
- Кредитная заявка на экране клиента: цель, сумма (UZS), срок (мес.), валюта.
  Авто-промоушен `lead`/`draft` → `recommendation` после заполнения 4 полей
  (`artifacts/api-server/src/routes/mini-app.ts:1510-1542`).
- Каталог кредитных продуктов: 60 строк (20 продуктов × 3 сегмента: micro/small/medium),
  ставки в UZS/USD/EUR, сроки по типам, льготный период (`lib/db/src/schema/...`).
- Сканирование документов с PaddleOCR (рус.), извлечение полей: ФИО, паспорт,
  ДР, телефон, адрес, VIN, госномер, ИНН (СТИР), модель/марка ТС
  (`artifacts/api-server/src/routes/mini-app.ts:794-814`).
- Калькулятор: аннуитет/дифференцированный, льготный период, валюта
  (`artifacts/api-server/src/lib/calculations.ts:37-198`).
- Корзина продуктов → автоматическая генерация PDF КП
  (`artifacts/api-server/src/routes/mini-app.ts:1987-2120`).
- Отправка КП через Telegram-бота, fallback в WhatsApp.
- Минимальный учёт залога (`collateralEstimates`, `collateralItems`).

### 1.3 Логические пробелы в существующем

- **Status enum допускает любые переходы.** В `PUT /mini-app/clients/:id` (`mini-app.ts:1490`)
  присваивается `updates.status = status` без проверки графа переходов. Эксперт
  может случайно/намеренно перескочить с `draft` на `approved`. Должен быть
  fixed-graph: `{draft → lead, lead → recommendation, recommendation → basket,
  basket → pdf_generated, pdf_generated → under_review, under_review →
  {approved|rejected}, approved → completed}`. Откат `approved → draft` должен
  быть запрещён.
- **Reassign не валидирует target user.** В `PUT /clients/:id`
  (`artifacts/api-server/src/routes/clients.ts:256, 278`) `assignedToId` принимается
  без проверки: пользователь существует / активен / роль `hunter` / филиал
  совпадает с филиалом клиента. Можно назначить клиента деактивированному юзеру
  или admin'у головного офиса.
- **Калькулятор без контекста продукта.** Поле `productName` в запросе —
  свободный текст, никак не связан с `credit_products.id`. Нет связи лимитов и
  ставок с фактическим продуктом из каталога.
- **Auto-promotion не блокирует возврат назад.** Если клиент уже в `basket`, а
  эксперт меняет одно из полей заявки — текущий код не понижает статус, но и не
  логирует факт изменения утверждённой заявки. По-хорошему — изменение полей
  заявки в стадиях `pdf_generated+` должно быть запрещено или логироваться как
  re-quote.
- **OCR-результаты не валидируются.** Если OCR неправильно прочитал паспорт, в
  поле `passportNumber` попадёт мусор. Нет проверки формата.

## 2. Админ-панель

### 2.1 Что работает корректно
- Auth с Bearer токеном, in-memory сессии (для тестов ок, для прод — хранилище
  должно быть Redis/DB).
- RBAC соблюдается на API: `requireRole`, `requirePermission` корректно
  закрывают write-операции для `branch_head`.
- Branch-scope для `branch_head`: видит только свой филиал по dashboard,
  clients, users (`dashboard.ts:31`, `clients.ts:76`).
- Dashboard метрики, фильтры, экспорт CSV branch-stats.
- CRUD-страницы Clients/Products/Branches/Users/Articles/CreditProducts/SapCodes/
  CreditLines: дизайн консистентный, использует shadcn-диалоги.
- Bulk import пользователей через XLSX с маппингом RU/UZ/EN заголовков, авто-
  генерацией паролей, превью перед коммитом.
- CSV/XLSX export через `XLSX.writeFile` (правильный формат, имя файла `.xlsx`
  корректно — функция называется `downloadCsv` по историческим причинам, но
  пишет XLSX, см. `artifacts/admin/src/lib/csv.ts:1-10`).

### 2.2 Найденные баги (см. также раздел 3)
- Reassign-диалог в `client-detail.tsx` показывает ВСЕХ пользователей, включая
  суперадминов и пользователей других филиалов. UX позволяет выбрать кого
  угодно — API не валидирует.
- На клиентах нет фильтра «без назначенного эксперта».
- На `clients.tsx` кнопка Import корректно скрыта для `branch_head`
  (`isBranchHead` flag, line 86, 235), но кнопка **Export** показывается всем —
  это продуктовое решение, не баг.
- Импорт клиентов разрешает `assignedToId` без проверки роли target user.
- Activity Log виден только super/head_office (`App.tsx:159`), но нет фильтра
  по типу события «client_status_changed» отдельно от «client_reassigned» —
  событий слишком много в общей куче.
- При импорте users пароль либо берётся из колонки, либо генерируется. При
  ре-импорте того же пользователя строка скипается (`duplicate_telegram_id`),
  но в response пишется только в `skipped` без причины-человеком.
- Reassign не понижает / не повышает статус, не уведомляет ни старого, ни
  нового эксперта.
- Кнопка submit в формах (`users.tsx:181-206`, `clients.tsx`) не disabled
  во время выполнения mutation в части кейсов (есть `isPending`, но используется
  не везде последовательно).
- Поиск по клиентам — client-side `filteredUsers.filter(...)` (`users.tsx:318`)
  работает по уже загруженным 20 строкам страницы. На большом наборе ищет
  только в видимой странице.

### 2.3 RBAC дыры
- `PUT /api/clients/:id` (admin route) принимает `assignedToId` от `branch_head`?
  Проверим: `clients.ts:240-260` использует `requirePermission("client.write")`.
  В `role-permissions.ts:34-45` `branch_head` не имеет client.write — ок,
  закрыто.
- `POST /api/users` от не-admin — закрыто `requireRole("superadmin",
  "head_office_admin")` — ок.
- `branch_head` не может массово удалять — закрыто.

### 2.4 Косметика / i18n
- В `clients.ts:22-32` константа `STATUS_LABELS` хардкодит узбекские лейблы.
  Используется в логах (Activity log) → лог всегда на узбекском, независимо от
  языка интерфейса. Для бэка это ок (логи внутренние), но если фронт показывает
  логи как есть — будет несоответствие.
- В админке есть страница `/recommendations`, но AGENTS.md явно говорит «auto-
  recommendation engine удалён в Phase E». Проверить, не показывает ли страница
  пустоту/ошибку.

### PDF — что выводится сейчас (проверено)

`pdf/leave-behind.ts` (215 строк) рендерит ОДНУ страницу A4:
1. Шапка «IPAK YO'LI Bank» + название филиала + заголовок «Индикативное предложение / Indikativ taklif».
2. Имя клиента.
3. Карточка «Интерес клиента / Mijoz qiziqqan kredit»: цель, продукт, сумма, срок/ставка, ориентировочный платёж. Если расчёта ещё нет — фолбэк-фраза.
4. Карточка «Залог / Garov»: принятая стоимость, покрытие, максимальный кредит, статус «достаточно/недостаточно», список первых 3-х предметов залога.
5. Карточка «Кредитный эксперт» с именем + крупным номером телефона.
6. Внизу — дисклеймер о предварительном характере документа.
