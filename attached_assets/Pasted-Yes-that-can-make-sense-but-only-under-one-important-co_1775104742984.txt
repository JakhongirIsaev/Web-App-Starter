Yes — **that can make sense**, but only under one important condition:

**If prod is on Airnet, then the AI part should also run under your control there or on another approved local server.**
If your app is on Airnet **but still sends raw client docs to OpenAI/Gemini**, the main legal/compliance risk does **not** disappear, because the sensitive transfer still happens outside your controlled local stack. ([airnet.uz][1])

What Airnet seems suitable for:

* hosting the **backend**
* hosting the **Telegram bot**
* hosting the **admin web app**
* hosting the **Mini App frontend**
* hosting the **database**
* possibly hosting a **local OCR/document extraction service** too

Why it is a reasonable local option:

* Airnet says its servers are in **Tashkent**, that **data storage and processing takes place on the territory of Uzbekistan and in the TAS-IX zone**, and it offers VPS/VDS and dedicated servers. ([airnet.uz][1])

## The key legal difference

### Safe-er structure

* Mini App
* Bot
* Backend
* DB
* OCR/AI service
  all hosted on Airnet or another local controlled server

### Still risky structure

* Mini App and backend on Airnet
* but client documents go from backend to OpenAI/Gemini

That second setup is still a cross-border third-party transfer problem in practice, even if the main app is local.

## What I would do on Airnet

### Option 1 — best practical MVP

Host on Airnet:

* FastAPI backend
* PostgreSQL
* Telegram bot
* admin web app
* Mini App frontend
* **PaddleOCR** or another local OCR/document parser

This is the strongest low-cost route for car documents.

### Option 2 — heavier

Host on Airnet:

* everything above
* plus a fallback local vision model

But this only makes sense if Airnet can provide enough hardware.

So for app + bot + DB + basic OCR:

### Likely okay on Airnet

* app + bot + admin + DB on VPS/VDS or small dedicated, depending on load

### Probably not good on standard VPS

* a heavier self-hosted multimodal model
* GPU-based inference
* big document-AI workload at scale

I could **not verify a public GPU server offer on Airnet’s site**, so for heavy local AI I would not assume they have it unless their sales team confirms a custom solution. ([airnet.uz][2])

## My blunt recommendation

### If you want production with real client docs:

Use Airnet only if the architecture is:

* **Airnet-hosted app**
* **Airnet-hosted DB**
* **Airnet-hosted bot**
* **Airnet-hosted local OCR/AI service**
* **no raw client docs sent to foreign public AI APIs**

That is the clean version.

### If you want cheap first production/pilot:

Start with:

* Airnet VPS/VDS
* backend + bot + admin + mini app
* Postgres
* **PaddleOCR local service**
* human review after extraction

That is much more realistic than trying to run a big visual LLM from day one.

## Best architecture on Airnet

### Small production / pilot

1. **Server 1**

   * FastAPI backend

   * Mini App static/frontend

   * local OCR service

Or for very tight budget:

* combine app + bot + DB on one machine first,

## Final answer

**Yes, Airnet can be a reasonable local production host for Minerva** because it offers local hosting in Tashkent/TAS-IX and VPS/VDS/dedicated options. ([airnet.uz][1])

But the important rule is:

**Hosting on Airnet helps only if the AI/document processing is also kept under your control.**
If “AI is part of it” just means “the Airnet-hosted backend calls OpenAI,” then the sensitive-data problem is still there.

My recommendation:

* **Airnet for app + bot + DB**
* **local OCR/AI on Airnet if possible**
* **do not use foreign public AI for raw client docs in prod**
