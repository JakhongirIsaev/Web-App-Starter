## 1. What the project is

**Minerva / Credit Hunter** is a Telegram-based SME sales operating system for bank credit specialists.

It has 3 parts:

* **Telegram Mini App** for hunters and branch heads
* **Web Admin App** for head office and superadmin/admin/editor roles
* **Telegram bot** as entry point and helper channel

The original concept already fixes that structure: Mini App is the main working tool, web app is for head office management, and the bot is auxiliary. 

The business problem is also already clear:

* workers are trained manually for too long,
* there is no good field tool,
* there is no leave-behind document for the client,
* data is collected manually and gets lost,
* management lacks visibility. 

## 2. Main goal

The goal is not to replace CRM now.

The goal is:

* help hunters work faster in the field,
* recommend suitable products,
* generate a professional proposal,
* keep client data inside temporary CRM-lite,
* show branch and management activity,
* later connect to EspoCRM after approval.

That matches the draft: CRM replacement is out of MVP, and EspoCRM comes later. 

## 3. Roles

### Superadmin

Full control over everything.

### Head office admin

Manages products, content, users, branches, visibility.

### Editor

Works with products and knowledge content.

### Branch head

Sees workers of their branch, branch client activity, and branch metrics.

### Hunter / branch worker

Main field user of the Mini App.

The original role model already includes superadmin/admin/manager/hunter, and your current web logic already has `superadmin`, `head_office_admin`, `editor`, `branch_head`, `branch_worker`.

## 4. Access and security logic

The whole system is controlled by **Telegram identity**.

### Core access rule

A user gets access only if:

* Telegram auth is valid
* backend validates it
* `telegram_id` exists in the system
* user is active
* role is allowed

If Telegram auth is valid but the user is not registered or is inactive, access is denied. Your current web app already follows exactly that logic. 

### Sensitive data rule

If a worker leaves:

* superadmin, head office admin, or branch head must be able to deactivate/remove access quickly,
* former workers must not keep access to branch or client data.

### Branch structure

The system must support:

* branches
* users assigned to branches
* branch heads
* worker visibility limited by branch

That branch-based foundation already exists in the current data model.

## 7. Mini App: main client flow

This is the main operational process.

### Step 1. Hunter opens Mini App

User enters through Telegram, already bound to their identity, role, and branch.

### Step 2. Create new client draft

This should be understood as **draft client session**, not necessarily full final client profile.

Why: in your later logic, the final client name can be requested before PDF generation, not necessarily at the very first second.

At this stage the system creates:

* draft client card/session
* branch link
* hunter link
* timestamp

### Step 3. Questionnaire / need assessment

Hunter asks the client several questions.

The internal logic can later be:

* rule-based
* AI-based
* hybrid

That decision is still open in the draft. 

The purpose is fixed:

* understand the need
* determine suitable directions
* recommend products

### Step 4. Recommendation result

The system recommends:

* **credit products**
* **non-credit products**

This is important: both groups must be present, not only credit.

### Step 5. Manual adjustment by hunter

After recommendations, the hunter goes to product selection area.

There the hunter can:

* review recommendations,
* open categories,
* manually add/remove products,
* override recommendation if needed.

This is important because specialist judgment must stay in control.

### Step 6. Basket

All chosen products go into **basket**.

Basket is not a retail cart.
It is a **proposal assembly area**.

It should contain:

* selected credit products
* selected non-credit products
* attached calculator result if present
* later maybe notes/language

### Step 7. Calculator

If a credit product is selected, hunter opens the calculator.

### Step 8. Final client-facing fields

Before PDF generation, app can ask for:

* final client name
* language
* maybe final contact data if needed

That resolves the “create new client first, but ask name later” contradiction.

### Step 9. Generate КП / PDF

System generates client-facing proposal PDF.

### Step 10. Save everything into client card

Everything must persist into CRM-lite:

* answers
* recommendations
* selected products
* calculations
* PDF
* timestamps
* notes
* hunter/branch data

#### Behavior

  * rate range

  * allowed repayment types
  * grace period rules
* Validation should happen automatically
* Hunter must be able to:

  * calculate
  * save result
  * add calculation to basket
  * use result in PDF

### Calculation formulas

The original spec already defines:

**Annuity**
`P = S × [r × (1 + r)^n] / [(1 + r)^n — 1]`

**Differentiated**

* principal = `S / n`
* monthly interest = remaining balance × rate
* payment = principal + interest

That is already formalized in the draft.
